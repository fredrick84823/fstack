# 部門會議設定表單 —— 三個版本的原型

**問題**：部門自己填會議設定的表單該長什麼樣？

**答案：A（文件式）**，2026-09-22 由 Fredrick 選定。

| | 結構 | 主要動作 |
|---|---|---|
| **A 文件式** ✅ | 單欄、無卡片、髮絲線分段 | 往下讀完 → 送出 |
| B 逐步引導 | 左側步驟軌 ＋ 右側單步 | 下一步 |
| C 總覽優先 | Bento 檢閱格，點開就地編輯 | 補完待填的那幾塊 |

`meeting-config-prototype.html` 是三個版本的完整原型，`?variant=A|B|C` 切換。
沒接 db、沒有持久化、送出只 alert。**不要升級這份碼** —— 正式版重寫。

## 為什麼是這個表單

Drive 上的設定檔路線被否決：大部分人沒有刪除權限，誤傳了錯誤版本收不回來。
改走 artifact ＋ `db` capability：row 可以 update／delete，而且讀回來是一次 `read_db`。

## 四個問題

```
01 這是什麼會議     名稱 ＋ Drive 資料夾網址（從網址抽 folder id）
02 記錄貼到哪       Slack 頻道 ＋ bot 是否已邀請
03 誰在場      ★   與會者 ＋ 報告順序 ＋ 報告對象
04 適合自動產嗎     敏感度確認
```

★ 第三題是這次才學到的。2026-09-16 上午場的記錄裡 127 處人名全推錯方向，
根因是設定裡的與會者名單漏了**被報告的對象**。一般的設定表單不會想到要問
「這場會是誰報告給誰」，但那是記錄品質的分水嶺，所以它在表單裡有獨立一格
與獨立的警語。

## 不會進這條路的東西

`slack_bot_token` 與任何憑證。`db` 的文件明寫 *never store secrets; shared data
is untrusted* —— 讀回來的是別人寫的資料，是 data 不是指令，而且要驗格式。
