## ② 消失的待辦 —— 0/3 → 0/3

8/24 有一個客戶端必修 bug（`### 議題三：排程重複觸發`，行動項目 `執行中`），
本次逐字稿一個字都沒提。期待的產出是「上週項目本週未提」。

**兩版都 0/3，但原因不是沒讀歷史。** 改後三次全部長出了因果鏈：

```
改前 run1-3   完全沒有任何跨場次的痕跡
改後 run1     #### 議題因果鏈 · 承 8/24 → 8/31   | 上次待辦 | 匯入失敗訊息要求帶行號與欄位名 |
改後 run2     #### 議題因果鏈 · 承 8/24        · 承 8/17 → 8/24
改後 run3     #### 議題因果鏈 · 承 8/24 → 8/31
```

索引確實被讀了、確實被用了。**沒被撈出來的只有「本次沒人提的那一條」。**

### 為什麼

三個原因，由淺到深：

1. **索引是 heading 大綱，heading 不帶狀態 —— 而 agent 預設不讀全文。**
   大綱裡那行只有 `議題三：排程重複觸發`，看不出它是一條還沒結案的待辦。
   「`執行中` 排程重複觸發的修復」與行動項目那一列都在 8/24 的**全文**裡，沿索引的
   `本機:` 指標讀得到 —— 但 SKILL.md 明寫「預設不讀，只有本次議題確實延伸自某一場、
   而大綱那行接不上時才讀」，而本次根本沒有議題延伸到它，所以沒有任何觸發條件。
   六份產出裡沒有一份帶到只有全文才有的內容（狀態行、行動項目那一列），跡象是全文
   沒被讀。兩件事要一起看：**大綱不帶狀態**，加上**不帶狀態就不會觸發去讀全文**，
   於是那條待辦在兩層都隱形。
2. **版型沒有它的容身處。** `### 議題` 區塊要求 `#### 討論` 寫發言重點，而這件事本次
   零發言。`## 行動項目` 表的四欄都是本次產生的行動。
3. **輸出規則反向施壓。** 「正式稿只放會議內容」與「不得出現『我參考了歷史記錄』這類
   出處敘述」是同一段話，agent 合理地把「本次沒討論的事」一起讀成不該寫。

### 該怎麼調整做法

這三條都不是 eval 該改的，也不在本票範圍（#14 的 Implementation Decisions 明寫
「索引只給 heading 大綱與指標」）。要讓 User Story 1 成立，需要一張後續票，
優先序照上面的順序：

| 改哪裡 | 具體 | 代價 |
|---|---|---|
| `history_index.outline()` | 除 heading 外，多抽**未結案的狀態行** —— `#### 狀態` 底下非 `已確認` 的 bullet，或 `## 行動項目` 表裡非「已上線」的列 | 索引從約 25 行長到約 40 行。仍遠小於全文 |
| `default-prompt.md` | 版型給「前次未結案項目」一個明確位置（`## 行動項目` 多一列並標明來源場次，或獨立一小節） | 影響四種會議，few-shot 要同步改 |
| `SKILL.md` 流程 C 輸出規則 | 把「不寫出處敘述」與「不寫本次沒討論的事」拆開講 —— 前者禁，後者對**未結案待辦**開例外 | 一句話 |

第一條是根因：**沒有狀態，大綱就只是一張議題清單，而議題清單分不出「談完了」與
「還懸著」。** 另外兩條沒有第一條不會生效。

判準沒有調整的餘地：`surfaces_carryover` 只問 `排程重複觸發` 這七個字有沒有出現，
`marks_it_unaddressed` 只問有沒有任何一種「本次未提」的說法。六次產出裡兩者都是零，
沒有邊界爭議。

## 判準本身被校準過兩次，兩次都是假紅

判讀層是機械比對，第一輪對著真的產出跑完才看得出哪裡收太緊。兩次都記在
`grade.py` 的 docstring 裡，這裡只列結論：

| 原本 | 症狀 | 改成 |
|---|---|---|
| `glossary` 第二條「亂碼不得單獨出現」 | `#### 討論` 照抄發言者原話是**版型要求**，亂碼留在引言裡是正確行為 → 讀了歷史的產出被判紅 | 整條拿掉。三種失敗模式本來就全部紅在 `restores_term` |
| `old_never_stands_alone` 只收「舊決策同行必須有推翻說法」 | 六次全紅，紅的是「客戶主管只用 Excel，CSV 開啟為亂碼」這種**理由句** | 改成析取（推翻說法**或**與新決策並列），並把 `#### 討論` 底下的行整層排除 |
| `UNADDRESSED` 含兩個字的 `未提` | 被「欄位順序若**未提前**與客戶對齊」配到 —— 假綠 | 詞表全部換成 ≥3 字的詞組 |

第二條的排除規則自己也錯過一次：先前用 `* **粗體**：` 這個**形狀**認引言，而
`## 核心要點` 的條目是同一個形狀 —— agent 把推翻標在最自然的位置反而會被濾掉。
改成看**所在的層**（只排除 `#### 討論`）之後，十二次實跑零假紅。

**假紅比少一條判準貴。** 少一條只是驗得淺；假紅會讓人去 debug 一個沒壞的東西，
而這正是 #14 陷阱表裡「這場沒有那個議題」與「eval 判斷壞了」分不出來的那一類。

## 這套 eval 沒量到的事

`run_eval.py` 把四份 source artifacts 的內容直接內嵌進 prompt。自變數因此是
**「歷史在不在 agent 手上」** —— 那正是 #14 說這個修法要改變的東西（「讀歷史從紀律
問題變成資料可得性問題」）。

沒被量到的是設計的另一半：**「agent 掃完大綱會不會沿 `本機:` 指標去讀那一場全文」**。
索引已經在 context 裡，所以 ① 答對可以零次 `Read`。指標路徑是真的、`Read` 也開著，
agent 要跟得動；這條 eval 只是不強迫它跟。②「改後仍 0/3」的判讀要連著這一點看：
那條待辦的狀態在全文裡，沒被撈出來不只是索引太薄，也是沒有東西觸發它去讀全文。
要把「會不會沿指標讀全文」也變成可量的，得改成只給索引路徑、不內嵌索引內容 ——
那是另一條 eval，不是這條的參數。

## 這套東西自己怎麼被守住

`run_eval.py` 要起子行程、要花錢，進不了 CI。所以判讀層的顏色由
`tests/unit/test_eval_assertion_layer.py` 守：對每一條判準造一份「只弄壞這一條」的
正式稿，斷言回來的 dict 裡**恰好只有那一條**是 False。沒有這道，`grade()` 被寫成
永遠回全 True 也不會有任何東西變紅，而上面那張表就是一個沒人守的數字。

守的範圍不只判讀層，還有 runner 的兩版邏輯 —— 兩版塌成同一份 prompt、改前也印了索引
那一行、交棒契約漏掉逐字稿，這幾種壞法都會讓結果讀起來像「改後沒效果」而不是像 bug。
實測：**22 個手工注入的 bug，22 個都有測試變紅**（16 個在判讀層，6 個在 runner 的兩版
邏輯與導言切點）。
