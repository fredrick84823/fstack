## 4 種 Skill Eval Test Case 設計模板

請依照指定 skill 的使用場景，根據下面這 4 種測試案例模板，產生對應 skill 的 eval / test cases。

---

### 1. Golden Reference 已知答案比對型

適合情境：
API / Library 文件查詢、資料分析、KPI 查詢、Runbook 驗證、任何「已經有正確答案」的任務。

可以這樣問 agent：

```text
我正在設計一個 skill，目標是協助使用者完成以下任務：

【skill 使用場景】
請填入：這個 skill 要幫使用者完成什麼工作？

這類任務有明確的正確答案，因此我想用 Golden Reference 的方式設計測試案例。

請幫我產生 5～10 個測試案例，每個案例都包含：

1. 使用者輸入
2. 不應該讓 agent 看到的標準答案
3. 評估方式
4. 通過條件
5. 可能踩雷的錯誤答案
6. 這個測試案例想驗證的能力

請特別注意：
- 測試資料應該盡量來自真實歷史資料或真實情境
- 不要只測正常案例，也要包含邊界條件
- 測試案例要能驗證 skill 是否真的理解文件、資料或規則，而不是只產生看似合理的回答
```

---

### 2. Rubric + Scenario 主觀品質型

適合情境：
會議記錄、週報、提案、結案報告、摘要、社群貼文、商業流程自動化、任何「沒有唯一正確答案，但有品質標準」的任務。

可以這樣問 agent：

```text
我正在設計一個 skill，目標是協助使用者產生以下內容：

【skill 使用場景】
請填入：這個 skill 要產生什麼內容？例如會議記錄、週報、提案、摘要、社群貼文等。

這類任務沒有唯一正確答案，因此我想用 Rubric + Scenario 的方式設計測試案例。

請幫我產生一組測試案例，包含：

1. 典型情境
2. 邊界情境
3. 異常情境
4. 一個好的輸出範例
5. 一個不好的輸出範例
6. 可逐項 Yes/No 判斷的 Rubric
7. 每個 Rubric 對應的通過條件
8. 常見失敗模式

請特別注意：
- Rubric 不要寫成「清楚」「完整」「有品質」這種模糊形容詞
- 每個標準都要能被具體判斷
- 請說明好範例與壞範例的具體差異
- 請設計讓 LLM evaluator 能穩定判斷的評估條件
```

---

### 3. State Transition 前後狀態驗證型

適合情境：
產品驗證、CI/CD、部署、自動化操作、資料更新、CRM / 後台流程、Infrastructure Operations、任何「執行後狀態應該改變」的任務。

可以這樣問 agent：

```text
我正在設計一個 skill，目標是讓 agent 執行某個操作，並驗證操作後的狀態是否正確。

【skill 使用場景】
請填入：這個 skill 會執行什麼操作？例如建立資料、更新設定、部署服務、修改設定檔、建立 ticket 等。

我想用 State Transition 的方式設計測試案例。

請幫我產生 5～10 個測試案例，每個案例都包含：

1. 前置狀態
2. 使用者輸入
3. agent 應該執行的動作
4. 預期後置狀態
5. 不應該被改動的狀態
6. 驗證方法
7. 通過條件
8. 失敗時可能代表的問題

請特別注意：
- 測試應該在隔離環境執行，例如 test repo、staging、sandbox、dry-run mode
- 不只要驗證「該改的有沒有改」
- 也要驗證「不該動的東西有沒有被動到」
- 請包含正常案例、邊界案例與錯誤操作案例
```

---

### 4. Adversarial / Counter-Example 找錯型

適合情境：
Code Review、文件審查、資安檢查、品質檢查、Runbook 診斷、任何「skill 的工作是找出問題」的任務。

可以這樣問 agent：

```text
我正在設計一個 skill，目標是協助使用者找出問題、風險或錯誤。

【skill 使用場景】
請填入：這個 skill 要檢查什麼？例如 code review、文件品質、資安風險、資料異常、流程漏洞等。

我想用 Adversarial / Counter-Example 的方式設計測試案例。

請幫我產生一組測試案例，至少包含：

1. Precision 測試：乾淨、沒有問題的案例，驗證 skill 不會亂報錯
2. Recall 測試：已知有問題的案例，驗證 skill 找不找得到
3. Trap 測試：看起來像問題、但其實不是問題的案例，驗證 skill 是否會誤判
4. 多問題案例：同時包含多個問題，驗證 skill 是否能完整找出
5. 模糊案例：需要根據上下文判斷的案例

每個測試案例請包含：

1. 測試輸入
2. 預期應該找出的問題
3. 預期不應該被標記的內容
4. 評估方式
5. 通過條件
6. 可能的 false positive
7. 可能的 false negative

請特別注意：
- 不要只測 skill 找不找得到問題
- 也要測它會不會太多疑、亂標紅
- 請讓測試同時覆蓋 precision、recall 和 false positive
```
