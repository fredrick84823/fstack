# Slack 交辦簡述

**這是交辦，不是報告。** 收件人不需要知道你做了什麼，只需要知道他要做什麼。

工程端寫給非工程端的訊息預設會失敗，因為寫的人手上有全部脈絡，於是把脈絡當禮貌一起送出去。對收件人來說那是雜訊：他要在十行技術名詞裡找出自己的那一行。

## 步驟

1. **列出收件人做得到的動作。** 不是「這件事的全貌」，是「他手上能執行的事」。轉一份檔案、決定一個選項、敲一個日期——通常不超過三件。做不到的事不進訊息。

2. **每個技術名詞問一次：他需要這個字才能行動嗎？** 不需要就刪，指向文件。路徑、IAM 角色、欄位名、環境變數、內部檔名——這些是「對方的工程師」要看的，不是收件人。留下的是他能感知的量：幾個檔、幾分鐘、幾塊錢。

3. **排成三塊**，順序固定：
   - **要做什麼** —— 動作 + 附件
   - **要對方回什麼** —— 明確到可以照抄
   - **需要你決定／我還缺的** —— 有選項就給推薦，並說清代價

4. **附來源連結。** PR、issue、檔案路徑擇一。訊息可以短，是因為背後有東西可追；沒有連結的短訊息只是資訊不足。

5. **收斂到八行以內。** 超過就是第 2 步沒做完。

完成條件：訊息裡每一行，都是收件人做得到的動作、要回傳的東西、要決定的事，或一個連結。有一行不屬於這四類就刪掉。

## 語氣

口語，但不寒暄。「麻煩幫忙轉一下 🙏」是口語；「不好意思打擾了，想跟您說明一下關於……」是寒暄。

有決策要對方做時，給推薦選項並標明代價：「對方自己開比較單純；我們開的話要先跟對方要 Google 帳號。」推薦與代價同一句，對方一眼看完就能決定。

## 判準

| 徵狀 | 位置 |
|---|---|
| 收件人要往下捲才看到自己要做什麼 | 三塊順序倒了 |
| 出現只有工程端唸得出來的字串 | 第 2 步漏掉 |
| 「補充說明」「另外值得一提」開頭的段落 | 那是報告的殘骸 |
| 沒有連結 | 第 4 步漏掉 |

## 例

**改前**（12 行，PM 讀完仍不知道要做什麼）

> @nina 味王杯麵市場分析的 SQL 交付包已備好，需要 PM 端轉給家樂福資料窗口。
> 交付內容：兩個檔案 run_all.sql ＋ README.md（Vendor Execution Pack）
> 對方要做的事
> 1. 取代 script 內兩個佔位字串：交易表全名、GCS bucket 名稱
> 2. 執行帳號需三個權限：專案層級 bigquery.jobUser、來源 dataset dataViewer、bucket storage.objectAdmin（不需要建表權限）
> 3. BigQuery console 整支 script 一次執行（勿分段，建議先對開頭 CREATE TEMP TABLE 做 dry-run 看成本）
> 4. 結果自動寫入 gs://<對方bucket>/weiwang_202604_202608/，整個資料夾完整回傳（含所有分片檔）
> 5. 回信只需回答一件事：有無改動 script 任何一行。執行時間、來源表名等 script 會自動寫進 _diagnostics__run_info，不用填表單
> …

第 1–4 點是 README 的內容，收件人不執行它們，對方的工程師才執行。

**改後**（6 行）

> @nina 味王杯麵的 SQL 交付包做好了，麻煩幫忙轉給家樂福窗口 🙏
>
> **附件兩個檔**：`run_all.sql` + `README.md`，對方照 README 跑一次就好，約 15 分鐘。
> **對方回什麼**：整包結果檔 + 一句「有沒有改到 script」。其他資訊 script 會自己寫進結果裡，不用填表。
>
> 有個前提要先確認：**結果要放誰的 GCS？** 對方自己開比較單純；我們開的話要先跟對方要 Google 帳號。
> 另外 #153 還缺三個日期（我方交付日／對方回件日／報告交付日），方便的話一起敲。
>
> 細節在這：<PR 連結>
